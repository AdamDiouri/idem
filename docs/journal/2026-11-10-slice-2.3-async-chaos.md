# Slice 2.3 — Async chaos with two API replicas

*Merged 2026-11-10 · [PR #10](https://github.com/AdamDiouri/idem/pull/10) · [plan](../superpowers/plans/2026-11-10-slice-2.3-async-chaos.md) · written retrospectively on 2026-11-10 from the PR and commit record*

Chaos campaigns now break the asynchronous paths on purpose, against two API replicas, and the verdict refuses to pass unless they really were broken.

Around this slice: [PR #8](https://github.com/AdamDiouri/idem/pull/8) moved compose secrets into a gitignored `.env`, and [PR #9](https://github.com/AdamDiouri/idem/pull/9) added Go profiling on internal ports and recorded the tracing design for milestone 3 (D20).

## What shipped

- **Two API replicas.** Clients send each request, retry and double click to the next replica in turn. Webhook deliveries rotate too, so a retry or duplicate reaches the other replica. API restarts hit one replica at a time.
- **Webhook faults in campaigns.** All six join the random fault sets. In runs of a minute or more, a dedicated block of six back-to-back 8s windows, one fault each, starts once traffic flows.
- **More failpoints.** `inbox_before_commit` (workers) and `webhook_after_insert` (API). Failpoints now name themselves when they fire, so the report counts each one.
- **A stricter verdict** for runs of a minute or more: every webhook fault had a real window with work in flight and fired, every armed failpoint fired, and every replica answered clients, accepted new webhooks and recognised duplicates.
- **Connection-pool metrics** (`idem_db_pool_*`) on every process, with an `IdemDBPoolSaturated` alert and runbook section.

## What broke or surprised us

- **The first version's verdict could pass without testing anything (two critical findings).** The independent reviewer reproduced both in real runs. Webhook-fault windows could start at t = 1 ms, before any traffic, and the verdict silently skipped them, so a 90s run could check no webhook fault at all. And the insertion logic cut other fault sets to 1 ms, breaking its own guarantee: a 60s run (seed 3379) passed with `dup_webhook` never firing. We replaced the gap-filling with the dedicated block and added a backstop. We then removed the backstop on purpose and its test failed.
- **Windows of exactly 5s were too tight.** A slow event just before one delayed its start, and it ran 4.99s. Each window is now 8s: 5s plus 3s of slack.
- **Sampling "work in flight" at one instant was wrong.** A window that opened right after a database restart sampled 0, although traffic flowed through all 7.8s of it. A window now counts if work was in flight at any event during it.
- **Our own review fix made a test flaky.** We had made "every replica recognised duplicates" a rule for every run, but only longer runs have the dedicated `dup_webhook` window, so a 30s run may legitimately see none. The rule now applies to runs of a minute or more.
- Review minors fixed: `Reproduce()` includes `--apis`; runs with only API failpoints are judged; `RunClients` with no replica reports instead of panicking; a process that never becomes ready shows the end of its log. That last one turned an opaque "not ready" into "this binary was built with `-tags nofailpoint`".

## Evidence

- A plan test across 8,000 plans (60s, 90s, 120s and 300s, 2,000 seeds each): every webhook fault has a dedicated window with slack after traffic starts, and every disruption kind still occurs.
- Campaigns after all fixes passed with 0 violations: seeds 1, 2, 3, 4, 5 and 1202 at 90s, and the reviewer's 3379 at 60s. Every webhook fault and all five failpoints fired; each replica served about half the requests and webhooks and recognised duplicates.
- Two guards passed from the start because Postgres already enforces them: the same key on two replicas gives one workflow (I6), and a webhook stored by a crashing replica and retried to the other is a duplicate.
- `make test`, `make lint` 0 issues, `make build-release`, chaos-tagged tests 3 times in a row, `promtool check config` (14 rules).

## Left open

- The verdict still could not tell whether webhooks did real work, since polling completes every payout anyway. An external review found this, and 2.3b fixes it.
