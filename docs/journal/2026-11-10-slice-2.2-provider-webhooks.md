# Slice 2.2 — Provider webhooks

*Merged 2026-11-10 · [PR #7](https://github.com/AdamDiouri/idem/pull/7) · [plan](../superpowers/plans/2026-11-10-slice-2.2-provider-webhooks.md) · written retrospectively on 2026-11-10 from the PR and commit record*

The provider now tells idem a payout's result by signed webhook. Polling from 2.1 stays as the safety net. Webhooks arrive late, duplicated and out of order, so idem treats each one as a prompt to ask the provider, never as the truth itself.

## What shipped

- **Signing** in Stripe's scheme (`t=…,v1=HMAC-SHA256`), compared in constant time, with a 5-minute replay window checked in both directions. The current and previous secrets both verify, so rotation needs no downtime.
- **Durable receipt.** `POST /webhooks/provider` verifies, stores the raw event in `webhook_inbox`, and only then answers `200`. A duplicate gets `200`, a store error `503` so the provider retries. Refused events are never stored.
- **The inbox processor** runs in every worker. It claims events under a lease, re-checks the payout with the provider, and applies the provider's current answer through the same transaction and hooks as a poll.
- **Disagreement is surfaced, never applied.** An event that contradicts a decided result is `IGNORED` as stale, or recorded as a `CONFLICT` that pages. An event about a parked workflow becomes `EVIDENCE` for the operator (D18). A recorded result is never changed.
- **Fake provider** sends signed webhooks with retries and six faults: duplicate, before the `202`, delayed, stale contradiction, dropped, badly signed.
- **Operators:** `PROVIDER SAYS` in `admin list`, audited `conflict list` and `conflict resolve`, new alerts, invariant I10, I4 extended to the inbox, and runbook sections including secret rotation.

## What broke or surprised us

- **A stale `payout.failed` could move money both ways (critical).** For a waiting payout, a stale or reordered failure event was applied without a check. A payout the provider had paid could be failed and the customer refunded. The independent reviewer reproduced it. Every event is now re-checked with the provider; an event ahead of the provider (still pending there) is deferred.
- **Evidence could stay pending forever.** A payout parked with no reference of its own (every send timed out, though the provider accepted it) could never be re-checked, so a real conflict never paged. The re-check now falls back to the event's payout ID, still checked against the step.
- **A ruling, not a fix.** An event whose re-check keeps failing retries at the backoff cap with no end state. A ceiling would turn a provider outage into ignored events; `IdemInboxBacklog` and polling already surface it.
- **Review minors fixed before merge:** orphan events now alert; events whose amount or currency do not match are ignored and logged; webhook secrets are trimmed and empty ones refused; unhandled event types are labelled `unsupported`, not `malformed`; the inbox got indexes and a retention sweep that never prunes evidence, conflicts or pending events.
- **Fake provider races.** A `fast_webhook` could in theory lose the race with its own `202` (microseconds wide, never reproduced). It is now held back until its request delivers it, guarded by a 30-payout stress test. Deliveries now run concurrently so one hanging receiver no longer blocks the rest.

## Evidence

- The reviewer confirmed the plan's five risk cases: a webhook during a poll, secret rotation, a replayed old webhook, an orphan event, and an operator acting during a re-check.
- Mutation checks: removing the re-check guard, applying to a step whose poll is in flight, or auto-resolving a parked step each fail their test.
- Chaos seed 1 (90s) passed with 0 violations: 712 payouts completed by webhook, 27 duplicates absorbed, 27 polls as the safety net.
- `make test` (15 packages), `make lint` 0 issues, `make build-release`, `promtool check config` (13 rules).
- Compose smoke: a payout completed about 2s after acceptance (`send` then `webhook`); a forged webhook got `400` and nothing was stored.

## Left open

- Webhook faults are not yet part of chaos campaigns, and only one API replica runs. Both come in 2.3.
