# Slice 1.1 — Skeleton and idempotent submit

*Merged 2026-11-09 · commits 73fb605..7e31808 (no PR) · [plan](../superpowers/plans/2026-11-09-slice-1.1-skeleton-and-idempotent-submit.md) · written retrospectively on 2026-11-10 from the commit record and the review labels (C1, I1, I2) in its regression tests*

The first slice gives idem a runnable binary, a Postgres schema and one endpoint: `POST /workflows`. The endpoint must be safe to call again. A client that times out and retries, or two identical requests that race, must end with exactly one workflow.

## What shipped

- The `idem` binary with `migrate` and `api` commands, Postgres 18 migrations, a container image and a compose stack (Postgres, migrate, API).
- `POST /workflows` creates a `payment_payout` workflow and its first `charge` step. The idempotency-key row, the workflow, the step and the stored response are written in one transaction. Nothing is acknowledged before `COMMIT`.
- Replays return the original `201` and a byte-identical body, plus `Idempotent-Replayed: true`, as Stripe does. The design doc said `200`; the plan changed it and updated the doc.
- The request fingerprint is computed from the decoded request, so a retry with different whitespace or key order still replays. The same key with a different body gets `422`.
- Keys are scoped per client: static API tokens map to a `client_id`. Concurrent requests with the same key are serialised by Postgres's unique-index wait, with no application locks. `SET LOCAL lock_timeout` bounds the wait and returns `409 idempotency_key_in_use`.
- The fee (`150` bps plus `25` cents by default) is fixed at creation and stored with the workflow. Amounts are `int64` cents throughout.

## What broke or surprised us

A review of the finished slice found three problems. Each was fixed in its own commit with a regression test.

- **A fee change could break retries (review C1).** Validation ran in the HTTP handler, before the key lookup. If the fee rose between a request and its retry, an amount that no longer covered the fee turned the retry of an existing workflow into a `422`. Validation now runs inside `Submit`, after the key lookup, so a retry of an existing workflow replays even if today's rules would reject its body. A request that fails validation releases its key, so the client can fix the body and reuse it.
- **A misconfigured fee could go negative or overflow (review I2).** Such a fee could slip past the "amount covers fee" check. The fee config is now bounded, and an invalid one is a server fault, not a client validation error.
- **Database work had no deadline (review I1).** A slow transaction could run past the server's write timeout and leave the client with no answer. Each request now has a deadline below the write timeout and answers with a status when it hits it.

## Evidence

- Integration tests for each failure mode in the plan: F1, a client retry after a timeout (`TestSubmit_ReplaySameKeySameBody`); F2, the same key with a different body (`TestSubmit_SameKeyDifferentBody`); F3, two identical submissions racing (`TestSubmit_ConcurrentSameKey`).
- HTTP end-to-end tests for the same three: `TestE2E_F1_RetryReplays`, `TestE2E_F2_DifferentBody`, `TestE2E_F3_ConcurrentPosts`.
- Tests for the plan's review focus: reformatted JSON replays, a new fee config does not change a replay, keys are scoped per client, a failure before commit leaves no trace, and a key held by an uncommitted transaction returns `ErrKeyInUse`.
- Regression tests for the review fixes: `TestE2E_RetryAfterFeeIncreaseReplays`, `TestNewPaymentInput_RejectsInvalidFeeConfig`, `TestPostWorkflows_RequestTimeout`.
