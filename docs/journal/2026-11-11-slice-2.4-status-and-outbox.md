# Slice 2.4 — Workflow status and the outbox

*Merged 2026-11-11 · [PR #15](https://github.com/AdamDiouri/idem/pull/15) · [plan](../superpowers/plans/2026-11-11-slice-2.4-status-and-outbox.md)*

The shop can now learn the true outcome of its payment. It can ask (`GET /workflows/{id}`), and every outcome is also recorded as an event in an outbox, in the same transaction that decides it, ready for the relay in slice 2.5 to deliver.

## What shipped

- **`GET /workflows/{id}`.** A client reads only its own workflows; another client's and an unknown one get the same `404`. The response has `status` (`processing`, `succeeded`, `failed`, `compensated`) and, for a failure, a `reason`. Parked workflows show as `processing`: parking is internal.
- **One definition of what a shop sees.** The SQL function `workflow_view` builds the JSON. The outbox stores its output at the transition and `GET` returns it live, so the two cannot drift.
- **The outbox, written in one place (D13).** `transitionWorkflow` is the only code that ends a workflow, so it is the only writer of events: a terminal transition inserts its event in the same transaction, and a second event for the same workflow fails the transaction.
- **A failure reason the shop can use.** The provider's refusal code (`card_declined`) used to survive only inside error text. Steps now keep it in `failure_code`; anything that is not a plain short code falls back to `charge_failed`, so raw provider text never reaches a shop.
- **Invariant I8** in every chaos run and in `idem check`: every terminal workflow has exactly one event, of the right type, whose payload is still its view; no other workflow has one.
- **Upgrades are clean.** Migration 00014 backfills events for workflows that ended before the outbox existed.

## What broke or surprised us

- **The spec's response format was a string to parse.** It said `"outcome": "failed: card_declined"`. We proposed two fields, `status` and `reason`, so a shop branches on one and displays the other; the owner approved, and the spec now says so.
- **A failing test hung the whole run.** A rollback test asserted inside an open transaction; when the assertion failed before the code existed, the test ended without rolling back, and closing the pool waited forever. The same trap had caught us in 2.3b. The rollback is now deferred right after `Begin`.
- **Two older invariant tests set `SUCCEEDED` by hand.** I8 rightly reported them: no real transition ends a workflow without its event. Their helper now writes the event the way a transition does, instead of I8 being weakened.
- **I8 could be stricter than planned.** The plan compared only the payload's status field. Nothing writes a workflow after it ends, so I8 compares the frozen payload with the live view byte for byte.

## Evidence

- Chaos campaigns, seeds 1, 2 and 3 (90s): PASSED, 0 violations. I8 held over 882, 903 and 888 terminal workflows, with workers killed at `before_commit` and `after_commit` and no relay running (F33: every event durable, none missing, none duplicated).
- Tests for every path to an outcome (worker completion, poll, webhook, refund, `admin fail`, `admin confirm-step`), for a rolled-back transition leaving no event, and for a second event failing the transaction.
- Compose smoke on a fresh database: three workflows reached `succeeded`, `failed` (`card_declined`) and `compensated` (`payout_failed`); each had one `PENDING` event equal to its view; unknown ID `404`, malformed `400`, no token `401`; `idem check` 0 violations.
- `make test` (15 packages), `make lint`, `make vuln` (0 vulnerabilities), `make build-release`.

## Left open

- Delivering events: the relay, signing, retries, `NO_ENDPOINT` for clients without a URL (D14, D19), the backlog alert, admin outbox commands, and the fake shop with invariant I9 are slice 2.5.
