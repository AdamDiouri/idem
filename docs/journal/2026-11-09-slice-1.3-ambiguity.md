# Slice 1.3 — Retries, dead letters and ambiguity

*Merged 2026-11-09 · [PR #2](https://github.com/AdamDiouri/idem/pull/2) · [plan](../superpowers/plans/2026-11-09-slice-1.3-retries-dead-letters-and-ambiguity.md) · written retrospectively on 2026-11-10 from the PR and commit record*

Every step must now end in success, a permanent failure, or a loud, named dead-letter state, within bounded time. Along the way the client learns to tell "may have moved money" from "provably moved nothing".

## What shipped

- **Backoff.** Retries use exponential backoff with full jitter. A provider's `Retry-After` raises the delay, capped at the backoff cap.
- **Sharper outcome classes.** A new `NoEffect` class covers answers that provably moved no money (`429`, refused connections, DNS failures). A `409` ("key in flight") is retried soon. A successful charge must report the requested currency.
- **Sticky doubt.** Once a step is `IN_DOUBT`, a later no-effect answer never sends it back to `PENDING`.
- **Dead letters.** When attempts run out, the step becomes `DEAD` with a `dead_reason`, and the workflow `NEEDS_ATTENTION` (parked for a human), in the same fenced transaction. The worker logs an ERROR with `money_may_have_moved`.
- **Key retention (F23).** An in-doubt step whose key is near the provider's retention limit is resolved by lookup, never by re-sending under a new key. A key the provider has forgotten ends `DEAD` as `key_expired_unknown`, with no new charge.
- **Stuck workflows and bounded shutdown.** The sweeper logs workflows that have not progressed for `IDEM_STUCK_AFTER`. The in-flight step gets `IDEM_SHUTDOWN_GRACE`, and its outcome is still recorded.

## What broke or surprised us

- **Go's HTTP transport resent a charge behind our back (critical).** When a reused connection drops, Go silently resends a POST that carries an `Idempotency-Key` on a new connection. If the provider read the charge and then died, the caller saw only the final "connection refused". The step was labelled `NoEffect` and could end `DEAD` claiming no money moved, although the customer was charged. An independent reviewer reproduced it. The client now uses `httptrace` and reports `NoEffect` only if the request was never written to any connection. A regression test covers it.
- **"Connection refused" is not proof of nothing.** The lesson from the bug above: a no-effect class is only safe if we know the bytes never left. We now check that directly instead of inferring it from the error.

## Evidence

- New failure tests: F11 rate limit retries without doubt; doubt stays sticky across a later `429`; F22 exhausted attempts go `DEAD` with the right reason; `DEAD` is fenced against a stale worker; F23 near and past retention resolved by lookup; a request sent before the provider dies is ambiguous; bounded shutdown.
- `make test` (all packages, `-race`, real Postgres 18), `make lint` 0 issues, `make build-release`.
- Compose smoke test:
  - a charge rate-limited twice recovered (`RETRY_NO_EFFECT` twice, then `SUCCEEDED`)
  - with every charge failing and `max_attempts = 2`, the step went `DEAD` (`attempts_exhausted_in_doubt`), the workflow `NEEDS_ATTENTION`, and the worker logged `money_may_have_moved: true`
  - `idem check` 0 violations

## Left open

- the fake provider answers a lookup of an in-flight key with `404` instead of `409`
- key age counted from an attempt that never reached the provider
- a run of `409`s uses up attempts quickly
- the worst-case shutdown time can exceed compose's grace period
- noisy stuck-workflow logs and a few lookup test gaps
