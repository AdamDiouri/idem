# Slice 2.3b: Hardening Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Close the gaps an independent review of milestones 1–2.3 found. Chaos must fail when the webhook path is broken. The invariants must catch lost or partial money movements they currently miss. The API, the ledger and the hooks must behave as the design promises.

**Architecture:**
- **Chaos and invariants.** Chaos stops judging before the provider's webhook queue has drained. The provider's delivery log (`GET /_webhooks`) becomes an oracle for a new invariant, `CheckWebhooks`, so the verdict can check what the inbox did, not only that payouts finished.
- **Schema.** Four small migrations: a UNIQUE key-to-workflow mapping, a counter that bounds failing hooks, one SQL definition of "money may have moved", and a restricted application role that cannot rewrite the ledger.
- **Everything else** is small, local fixes, each with a test that fails first.

**Tech Stack:** Go 1.25, Postgres 18, pgx/v5, sqlc, goose, testcontainers. The chaos harness (`internal/chaos`) is unchanged in kind.

**Spec:**
- [`docs/design.md`](../../design.md): §10 ledger, §12 failure modes, §13 invariants
- [`docs/superpowers/specs/2026-11-10-milestone-2-design.md`](../specs/2026-11-10-milestone-2-design.md): I8–I10, F15–F19, F30
- The review's findings, as triaged in conversation on 2026-11-10. The numbers in `[R#]` below refer to them.

## Global Constraints

- Commits never contain a `Co-Authored-By` line.
- Every behaviour change starts with a test that fails for the reason described.
- New migrations are `00010`–`00013`, each with a working `-- +goose Down`.
- New environment variables are validated in `internal/config`, and each error names the variable.
- `make test` (with `-race`, against real Postgres 18) and `make lint` stay green after every task.
- Chaos campaigns at the end:
  - seeds 1, 2 and 3 at 90s
  - seed 1202 at 60s
  - the chaos-tagged package tests three times in a row

  Each must pass with 0 violations.

## Review Focus

1. **The settle phase waits for webhooks that never finish**, for example a delivery stuck mid-send while an API restarts. Expected: the wait is bounded by `SettleTimeout`, and the report says how many deliveries were still in flight. A test belongs to Task 1.
2. **A query path the restricted role was never granted.** These run rarely: the admin commands, retention DELETEs, the sweeper. Expected: every integration test runs as `idem_app` (Task 9), and so does every chaos process. A missing grant then fails a test instead of production.
3. **Migration 00010 meets a database where two keys already share a workflow.** Expected: the migration fails with Postgres's unique-violation error naming the constraint. It must never silently drop a row. A test belongs to Task 3.
4. **A worker whose lease was lost records a hook failure.** Expected: the epoch fences the update, so the counter does not move and the step is untouched. A test belongs to Task 7.
5. **`Retry-After` is an HTTP date in the past, or years in the future.** Expected: 0 for the past, and the 1h cap for the future. A test belongs to Task 10.

**Interfaces:**

- Produces:
  - **The check:** `func CheckWebhooks(ctx context.Context, pool *pgxpool.Pool, deliveries []fakeprovider.WebhookDelivery) ([]Violation, error)`
  - **The query:** `-- name: InboxRowsForCheck :many`. It reads `SELECT i.provider_event_id, i.status, COALESCE(i.note,'')::text AS note, w.status AS workflow_status FROM webhook_inbox i LEFT JOIN steps s ON s.id = i.step_id LEFT JOIN workflows w ON w.id = s.workflow_id`. `workflow_status` is nullable.
  - **The report field:** `WebhookCounts` gains `StaleIgnored int \`json:"stale_ignored"\``.

**The rules.** Each item below is one violation per offending event. Every one is a bug against an honest provider.
- **I11a:** a delivery with `Delivered == true` has no inbox row. Detail: `"provider event <id> was acknowledged but is not in the inbox"`.
- **I11b:** a delivery with `Fault == "bad_signature"`, `Delivered == true` and `Attempts == 1`. Its only attempt carried a wrong signature, so the API accepted a forged webhook.
- **I11c:** an inbox row whose `provider_event_id` is in no delivery: an event the provider never sent was stored.
- **I10 (tightened):**
  - A non-stale delivery's row must be `PROCESSED`, or `EVIDENCE`.
  - A stale delivery's row must be `IGNORED` with note `stale`, or `EVIDENCE`.
  - `EVIDENCE` is allowed only when `workflow_status = 'NEEDS_ATTENTION'`.
  - Any other combination is a violation. That includes `IGNORED` with `orphan`, `malformed`, `unsupported…` or a mismatch note, and `IGNORED stale` on a non-stale event: a true event dismissed.
  - The existing `CONFLICT` check in `Check` stays as it is.

**Steps:**

**Interfaces:**
- Produces:
  - **The error type:** `type HookError struct{ Err error }`, with `Error()` and `Unwrap()`
  - **The function:** `func RecordHookFailure(ctx context.Context, pool *pgxpool.Pool, s ClaimedStep, hookErr error, max int, delay time.Duration) (dead bool, err error)`
  - **The worker option:** `WorkerOptions.HookMaxFailures int`

**The behaviour.** All of it happens in one transaction, fenced on `lease_epoch` like `Complete`. If the step is fenced, return `ErrFenced` and change nothing.
1. Increment `hook_failures`.
2. If the new value is below `max`:
   - **a send attempt:** the provider reported success, so money moved. The step goes to `IN_DOUBT` and the attempt row's outcome is `IN_DOUBT`.
   - **a poll:** the step goes back to `AWAITING_CALLBACK`, with the attempt outcome `AWAITING_CALLBACK`.
   - **either way:** `next_attempt_at = now() + delay`, the lease is cleared, and the attempt's `error` is the hook error.
3. Otherwise:
   - the step is `DEAD` with reason `hook_failed`, and its attempt outcome is `DEAD`;
   - `applyResult(ResultDead)` moves the workflow to `NEEDS_ATTENTION`.

The worker logs at ERROR `"step hook failed"` with `hook_failures` and `max`. Then it returns `RunResult{Claimed: true, StepID: s.ID}` and the error.
