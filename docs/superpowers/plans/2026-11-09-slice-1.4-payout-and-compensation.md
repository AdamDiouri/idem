# Slice 1.4 — Payout and Refund Compensation — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Complete the `payment_payout` saga end to end. After a charge, pay the merchant (amount − fee). If the payout *definitely* fails, refund the customer in full and mark the workflow `COMPENSATED`. Every money movement is posted to the ledger in its success transaction. The invariant checker proves the ledger agrees with the provider (I3), no payout happens without a charge (I5), and each terminal status matches what actually moved (I7).

**Architecture:** Payout and refund are two more `engine.Step` implementations on the existing claim → call → complete protocol, so they inherit leases, fencing, retries, dead letters and key-retention lookups unchanged. Payout is the **pivot** (design §8.1): only a definite payout failure triggers compensation. An ambiguous payout that runs out of attempts goes `DEAD` → `NEEDS_ATTENTION`, never refund, because the merchant may have been paid. Workflow transitions become compare-and-swap on the expected current status. Refund steps carry the charge they reverse in a typed `refund_charge_ref` column, frozen when the refund is created.

**Tech Stack:** As before; no new dependencies.

**Spec:** `docs/design.md` — §4 (GR1–GR5), §5, §8.1, §8.2, §9.1, §9.3, §10 (ledger table), §12 (F20, F21), §13 (I3, I5, I7), §14.1, §16 (D2, D9, D11).

## Global Constraints

- All slice 1.1–1.3 constraints hold (Go 1.25 pins; DB clock; fenced completion; stored keys never recomputed; sticky doubt; no attribution trailers).
- Ledger postings exactly as design §10, in signed cents:
  | Event | Entries |
  |---|---|
  | Charge succeeded | `provider_receivable +amount`, `merchant_payable −(amount−fee)`, `platform_revenue −fee` (existing) |
  | Payout succeeded | `merchant_payable +(amount−fee)`, `provider_receivable −(amount−fee)` |
  | Refund succeeded | `merchant_payable +(amount−fee)`, `platform_revenue +fee`, `provider_receivable −amount` |
  Zero-amount entries are omitted.
- Payout amount is `amount − fee`. Refund amount is the full charged `amount`.
- Max attempts: payout 8, refund 20 (design §9.3).
- **Compensate only on `FAILED_PERMANENT` payout.** A payout `DEAD` never creates a refund.
- Workflow status changes are CAS: `UPDATE workflows … WHERE id = $1 AND status = $expected`; 0 rows ⇒ error ⇒ the completion rolls back.
- Workflow transitions in this slice: `RUNNING → SUCCEEDED` (payout ok), `RUNNING → COMPENSATING` (payout failed), `COMPENSATING → COMPENSATED` (refund ok), `RUNNING|COMPENSATING → NEEDS_ATTENTION` (refund permanently failed, or any `DEAD`), `RUNNING → FAILED` (charge declined, existing).

## Decisions this plan makes (not in the spec)

- **Typed `steps.refund_charge_ref text` column** (chosen over a generic `params jsonb` after discussion): `CHECK ((name = 'refund') = (refund_charge_ref IS NOT NULL))`. It is set from the charge's `provider_ref` inside the payout's failure transaction. The database rejects a refund without its charge at insert time, and the column is indexable for reconciliation. A generic mechanism can come with milestone 2's workflow definitions if needed.
- **Fake provider endpoints** `POST/GET /payouts` and `POST/GET /refunds` share the charges idempotency machinery. Payouts answer `201 {"id":"po_…","status":"paid","amount_cents"}`. Refunds answer `201 {"id":"re_…","status":"succeeded","amount_cents"}`.
- **Deterministic failures:**
  - a `merchant_id` starting with `mer_invalid` → payout `422 invalid_account` (stored)
  - a refund whose `charge_id` is unknown, or whose amount exceeds the charge → `422 invalid_refund`
  - a new fault mode `payout_fail` (`422 invalid_account`) for the `payouts` endpoint, as listed in design §14.1
- **Fake lookup of an in-flight key returns `409`**, not `404`. This was a deferred slice 1.3 minor; it matters now because the real adapter will copy the fake's contract.
- **A refund that fails permanently** (`FAILED_PERMANENT`) sets the workflow to `NEEDS_ATTENTION`. The customer was charged and nothing reversed it automatically, so a human must act.

## Review Focus

1. **A payout that is ambiguous until its attempts run out must not be refunded.** The merchant may have been paid, and refunding as well would lose the platform money → Task 4 `TestFlow_PayoutDeadDoesNotCompensate`.
2. **A compensated workflow's ledger nets to zero on every account**, including the fee, and the refunded amount equals the full charge → Task 4 `TestFlow_PayoutFailsRefundCompensates_F20`.
3. **A refund the provider rejects** (unknown charge) must end in `NEEDS_ATTENTION`, never `COMPENSATED` → Task 4 `TestFlow_RefundRejectedNeedsAttention`.
4. **A workflow already in an unexpected state** (e.g. someone set it to `NEEDS_ATTENTION` by hand) must make the completion fail and roll back, not silently overwrite → Task 3 `TestTransitionWorkflow_RejectsUnexpectedStatus`.
5. **Many concurrent workflows with mixed faults** must all end terminal or in attention with zero violations of I1, I2, I3, I5 and I7 → Task 4 `TestFlow_ManyWorkflowsUnderFaults`.

### Task 1: Fake provider — payouts and refunds

**Files:** Modify `internal/fakeprovider/provider.go`, `faults.go`; Test `internal/fakeprovider/provider_test.go`.

**Interfaces — Produces:**
- `POST /payouts` body `{"amount_cents","currency","merchant_id","workflow_id"}` → `201 {"id":"po_<uuidv7>","status":"paid","amount_cents","currency"}`, effect `Type "payout"`; `merchant_id` prefix `mer_invalid` → `422 {"error":{"code":"invalid_account"}}` (stored, no effect).
- `POST /refunds` body `{"amount_cents","currency","charge_id","workflow_id"}` → `201 {"id":"re_<uuidv7>","status":"succeeded","amount_cents","currency"}`, effect `Type "refund"`. A `charge_id` that is not a charge effect, or an `amount_cents` greater than that charge → `422 {"error":{"code":"invalid_refund"}}` (stored, no effect).
- `GET /payouts?idempotency_key=`, `GET /refunds?idempotency_key=` like charges.
- Any lookup of a key still in flight → `409 idempotency_key_in_flight` (all three resources).
- Keys are namespaced per resource (the same key string on `/charges` and `/payouts` is independent).
- `Rule.Endpoint` ∈ `charges|payouts|refunds`; new mode `ModePayoutFail = "payout_fail"` (valid only for `payouts`; `422 invalid_account`, stored). All existing modes are valid on every endpoint.
- `Calls()` keys: `"POST /payouts"`, `"GET /payouts"`, `"POST /refunds"`, `"GET /refunds"` as well.
- Implementation: one handler factory `p.resource(name string, perform func(req) (status, body, *Effect))` so the idempotency, fault and retention logic exists once.

### Task 4: Payout and refund steps (F20, F21)

**Files:** Create `internal/engine/payout.go`, `internal/engine/refund.go`, `internal/engine/flow_test.go`; Modify `internal/engine/charge.go` (payout created through `newStep`).

**Interfaces — Produces:**
- `engine.NewPayoutStep(client *provider.Client) Step`:
  - `Name()` `"payout"`.
  - `Execute`/`Lookup` use `PayoutRequest{amount − fee, currency, merchant_id, workflow}`.
  - `OnSuccess`: post `PayoutEntries`, then `RUNNING → SUCCEEDED`.
  - `OnPermanentFailure`: read `ChargeProviderRef`, `newStep("refund", 20, ref)`, then `RUNNING → COMPENSATING`. If there is no successful charge, return an error, because that's an invariant breach.
- `engine.NewRefundStep(client *provider.Client) Step`:
  - `Name()` `"refund"`.
  - `Execute`/`Lookup` use `RefundRequest{amount, currency, s.RefundChargeRef, workflow}`. An empty ref (impossible given the CHECK) → `provider.Outcome{Class: Permanent}` with an error, defensively.
  - `OnSuccess`: post `RefundEntries`, then `COMPENSATING → COMPENSATED`.
  - `OnPermanentFailure`: `COMPENSATING → NEEDS_ATTENTION`.
- `ledger.Txn.Kind` values `"payout"`, `"refund"`.

Test harness: workers registered with all three steps (`h.allSteps()`); helper `h.drain(t, w)` calls `RunOnce` until `Claimed == false` (bounded at 100). Helper `workflowStatus`, `accountSums(wf) map[string]int64`. Every test ends with `invariants.Check` returning no violations. Task 5 widens that check to I3, I5 and I7; tests written now must still pass then.

### Task 5: Invariants I3, I5, I7

**Files:** Modify `internal/store/queries/invariants.sql`, `internal/invariants/check.go`; Test `internal/invariants/check_test.go`.

**Interfaces — Produces:** `invariants.Check` additionally evaluates:
- **I3 (ledger agrees with provider):** per `(workflow, kind)`, the number of provider effects of that type equals the number of ledger transactions of that kind. For each matching pair, the effect's `AmountCents` equals the sum of the positive entries of that ledger transaction. This works for all three kinds: charge `+amount`; payout `+(amount−fee)`; refund `(amount−fee)+fee`.
- **I5:** a workflow with a payout effect also has a charge effect.
- **I7** (terminal workflows only):
  - `SUCCEEDED` ⇒ ≥1 charge and ≥1 payout effect, 0 refunds.
  - `COMPENSATED` ⇒ charge and refund, 0 payouts.
  - `FAILED` ⇒ no effects.
  - `NEEDS_ATTENTION` and non-terminal workflows are not checked by I7.
- Queries: `LedgerTransactionsSummary :many` (workflow_id, kind, positive_sum per transaction) and `TerminalWorkflows :many` (id, status for `SUCCEEDED|FAILED|COMPENSATED`).
